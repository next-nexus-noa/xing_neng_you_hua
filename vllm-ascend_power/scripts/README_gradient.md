# Fixed Micro-Batched PP Gradient Experiments

This folder contains a two-process fixed-M sweep runner with automatic QPS
capacity calibration:

- `generate_gradient_plan.sh`: creates `gradient_plan.csv`
- `run_gradient_server.sh`: starts/stops `vllm serve` for each row
- `run_gradient_power_client.sh`: resolves calibrated QPS, runs
  `vllm bench serve`, samples power, summarizes the PP trace, and saves results

## 1. Generate the plan

```bash
bash scripts/generate_gradient_plan.sh gradient_plan.csv
```

The default plan contains:

- models: `Qwen/Qwen2.5-3B`, `Qwen/Qwen2.5-7B`, `Qwen/Qwen2.5-14B`
- datasets: GovReport-GAO (1K/2K/3K/3.5K/3.8K), LongBench-QMSum
  (1K/3K/3.8K), and STELLA-Corpus (1K/3K/3.8K)
- one saturated fixed-M=1 capacity probe for every dataset/model combination
- formal request rates: `0.35C`, `1.0C`, and `2.0C`, where C is the measured
  fixed-M=1 request throughput for that exact dataset/model combination
- formal micro batches: `1`, `2`, `4`
- num prompts: `200`

The generated plan has 33 capacity probes and 297 formal rows (330 total).
Every probe is immediately followed by low/medium/high rows, with each level
expanded to M=1/2/4. Override probe pressure or sample count when needed:

```bash
export CAPACITY_PROBE_RATE=10
export CAPACITY_NUM_PROMPTS=200
```

Edit `gradient_plan.csv` directly, or edit arrays in `generate_gradient_plan.sh`.

## 2. Configure the micro-batch switch

Different branches may expose fixed Micro-Batched PP differently.

If it is an environment variable:

```bash
export MICROBATCH_ENV_NAME=VLLM_ASCEND_PP_MICROBATCH
```

The micro-batch **count** is automatically passed as `VLLM_ASCEND_PP_MICROBATCH_NUM`
by `run_gradient_server.sh` (same value as the `micro_batch` column).

If it is a CLI argument:

```bash
export MICROBATCH_ARG_TEMPLATE='--num-micro-batches {micro}'
```

If your implementation uses another name, replace it there. The `{micro}` token is replaced by the value from `gradient_plan.csv`.

## 3. Run server side

In one shell:

```bash
export VLLM_USE_MODELSCOPE=True
export PYTORCH_NPU_ALLOC_CONF=max_split_size_mb:256
export PLAN=gradient_plan.csv
export RESULT_ROOT=gradient_results
export ASCEND_DEVICES=0,1
export TRACE_ENABLED=1
export TRACE_FILE=/workspace/vllm_ascend_pp_trace.jsonl
export MICROBATCH_ENV_NAME=VLLM_ASCEND_PP_MICROBATCH
bash scripts/run_gradient_server.sh
```

The server command is based on:

```bash
ASCEND_LAUNCH_BLOCKING=1 ASCEND_RT_VISIBLE_DEVICES=0,1 \
VLLM_ASCEND_PP_TRACE=1 VLLM_ASCEND_PP_TRACE_FILE=/workspace/vllm_ascend_pp_trace.jsonl \
vllm serve MODEL \
  --host 0.0.0.0 \
  --port PORT \
  --pipeline-parallel-size 2 \
  --tensor-parallel-size 1 \
  --dtype float16 \
  --enforce-eager \
  --no-async-scheduling \
  --max-model-len MAX_MODEL_LEN
```

Prefix caching is forcibly disabled so warmup KV cache cannot leak into the
capacity probe or formal measurement. The script prepends
`--no-enable-prefix-caching` to additional `EXTRA_SERVER_ARGS` and rejects an
explicit `--enable-prefix-caching`.

Use `EXTRA_SERVER_ARGS` for other flags:

```bash
export EXTRA_SERVER_ARGS='--some-flag value'
```

The trace file is generated by the server process. `run_gradient_server.sh`
removes the previous trace before every run and passes these variables to
`vllm serve`:

```bash
VLLM_ASCEND_PP_TRACE=$TRACE_ENABLED
VLLM_ASCEND_PP_TRACE_FILE=$TRACE_FILE
```

## 4. Run client side

In another shell, from the same directory:

```bash
export PLAN=gradient_plan.csv
export RESULT_ROOT=gradient_results
export TRACE_FILE=/workspace/vllm_ascend_pp_trace.jsonl
export TRACE_SUMMARY_SCRIPT=scripts/pp_trace_summary.py
export WARMUP_RUNS=1
bash scripts/run_gradient_power_client.sh
```

The client writes `$RESULT_ROOT/capacity_qps.csv`. Plan values `auto-low`,
`auto-medium`, and `auto-high` are resolved just before each benchmark using:

```bash
export LOW_QPS_FACTOR=0.35
export MEDIUM_QPS_FACTOR=1.0
export HIGH_QPS_FACTOR=2.0
```

The resolved numeric rate is written to `client_config.txt` and
`summary_power.csv`. If a capacity probe fails or reports failed requests, the
following automatic rows are marked failed rather than using a stale or
hard-coded QPS.

The client waits for each server run, executes one warmup benchmark with the
same parameters, removes the warmup trace, then executes the measured benchmark:

```bash
vllm bench serve \
  --backend vllm \
  --model MODEL \
  --endpoint /v1/completions \
  --dataset-name random \
  --random-input-len INPUT \
  --random-output-len OUTPUT \
  --num-prompts NUM_PROMPTS \
  --request-rate REQUEST_RATE \
  --host HOST \
  --port PORT
```

Only the measured benchmark is parsed into `summary.csv`. Warmup output is kept
as `warmup_1.txt` in each run directory for debugging.

Then it runs the trace summary for the measured benchmark:

```bash
python pp_trace_summary.py /workspace/vllm_ascend_pp_trace.jsonl --skip 5 --top-slow 10
```

and removes the original trace file after copying it into the result directory.

## 5. Results

Each run is saved under:

```text
gradient_results/RUN_ID/
```

Important files:

- `server.log`
- `server_config.txt`
- `benchmark.txt`
- `pp_trace.jsonl`
- `pp_trace_summary.txt`
- `client_config.txt`

The aggregate table is:

```text
gradient_results/summary_power.csv
```
